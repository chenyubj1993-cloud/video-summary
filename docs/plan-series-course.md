# 系列视频「课程化整合」技术方案 v0.1

> 目标：把一个 UP 主的整个合集（或一个收藏夹）吃进去，产出一份**能当课上的大纲**——有结构、有去重、有前后演化和自我修正，每个知识点都能跳回原片的那一秒。
> 状态：设计稿，未实现。所有数字标注了来源（实测 / 估算 / 待验证）。

---

## 0. 一句话定位

**不是「把 50 期各总结一遍再拼起来」，而是「把 50 期当成一门课来备」。**

差别在三个动作上，这也是全部价值所在：

1. **去重**：第 12 期讲过的概念，第 37 期又讲了一遍——课程里只保留一次，标注「详见 E12」。
2. **演化**：同一个知识点在 48 期里是怎么逐步加深的（先讲定义 → 再讲特例 → 最后讲反例）。
3. **修正**：UP 主自己在后面否定了前面的说法——这类「自我修正」单独成表。

现有工具（video-to-notes、lectural、OpenVideoSearch）都停在「单期」，第 1、2、3 条没人做。这就是空位。

---

## 1. 非目标（明确不做，避免烂尾）

- ❌ 不做多 UP 主的横向对比（先把单系列做对）
- ❌ 不做实时/直播
- ❌ 不做视频生成、不做搬运、不重分发原片
- ❌ 不做通用「视频转笔记」（已是红海）
- ❌ 不做云端服务/账号体系（本地优先，单文件输出）

---

## 2. 用户与场景

| 场景 | 输入 | 期望 | 成功判据 |
|---|---|---|---|
| 补课 | 某 UP 主的《线性代数》48 期 | 一份课程大纲，知道该按什么顺序看、哪几期可以跳 | 能直接照着大纲看完，不迷路 |
| 复习 | 已看完，想查「特征值那节在哪」 | 知识点 → 秒级深链 | 3 次点击内定位到原片 |
| 尽调 | 想判断这个 UP 主值不值得追 | 内容重复度、深度演化、自我修正次数 | 能形成判断并说出理由 |

第三类是最容易被低估的：**「这个 UP 主到底有没有货」**其实是长期观众最想知道的问题，而它恰好是「课程化」的副产品。

## 3. 系统分层

```
L0 发现与筛选   → 拿合集列表、元数据，决定哪些期值得处理
L1 取材         → 字幕优先，ASR 兜底（成本的大头在这里）
L2 单期结构化   → 章节切分 + 知识点 + 断言（带时间码）
L3 跨期聚合     → 主题聚类 → 课程大纲；重复检测
L4 修正检测     → 同一实体的说法变化
L5 产出         → course.md / index.html / conflicts.md / duplicates.md
```

### L0 发现与筛选

B 站接口（**需实测确认，部分要登录态**）：

- 合集/系列列表：`/x/polymer/web-space/seasons_series_list?mid=<mid>&page_num=1&page_size=20`
- 合集内投稿：`/x/polymer/web-space/seasons_archives_list?mid=<mid>&season_id=<sid>&page_num=1&page_size=30`
- 单期元数据：`/x/web-interface/view?bvid=<bv>`（含 cid、分P、时长、简介）
- 圈子/合集之外：`/x/space/wbi/arc/search` 需要 **wbi 签名**（`w_rid` + `wts`），是最容易踩坑的一环

筛选逻辑（省时间的关键）：

- 时长 < 3 分钟的（可能是预告/花絮）默认跳过，人工可覆盖
- 按**弹幕率**（弹幕数 / 播放数）和**收藏率**排序，先处理高信号期
- 标题做一次聚类，把「同题重录」的期找出来（这类通常一期就够）

### L1 取材：字幕优先，ASR 兜底

这是整个方案能不能跑起来的**成本命门**。

- 官方字幕：`/x/player/v2?aid=&cid=` 的 `data.subtitle.subtitles[]` 里有 `subtitle_url`（JSON，带 `from/to/content`）。**AI 字幕通常需要登录 cookie**，CC 字幕公开。待验证。
- 如果没有字幕 → 走现有 ASR 流水线（`summarize_video.py` 的 `Media.acquire()` + `transcribe()` 可直接复用）。
- 有字幕也要**抽检**：随机 3 期，用 medium ASR 跑一遍，算字幕的字错率。若字幕错字率 < 3%，全量用字幕，能省 90% 的时间。

### L2 单期结构化

输入：带时间码的句子流。输出：`chapters[]`，每章含 `title / start / end / points[] / claims[]`。

- **章节切分**：三种信号投票 —— ①句间停顿 > 1.5s 且语义断点（LLM 判断）②弹幕密度突增（换话题时观众会刷）③口头标记词（"接下来""那我们看""总结一下"）。3 分钟一期的粒度太细，长视频按 5–12 分钟一章。
- **知识点**：每章 3–5 条，必须写成**可检索的独立句**（"特征值之和等于矩阵的迹"），而不是"讲了特征值的性质"。这一步的措辞质量决定 L3 聚类成败。
- **断言（claim）**：从知识点里抽出可证伪的陈述，带原文引用 + 时间码。供 L4 用。

单期成本：转写 8k 字符 ≈ 1 次 3k token 的调用（分块时更多），输出 1k。可控。

### L3 跨期聚合

三步，顺序不能反：

1. **向量化**：所有知识点用 embedding 模型编码。本地 `bge-small-zh-v1.5`（~100MB，CPU 可跑）足够，或用 API。
2. **粗聚类**：HDBSCAN（不需要预设类数，允许噪声点），得到 20–60 个簇。
3. **LLM 归并命名**：把每个簇的知识点列表喂给 LLM，让它①命名②合并语义重复的簇③排出教学顺序（前置知识先讲）。

产出就是课程大纲。**排序原则**：依赖关系 > 原片顺序。原片顺序通常已经合理，只在检测到「第 3 期用了第 20 期的概念」时才调整。

**重复检测**：任两条知识点余弦相似度 > 0.92 视为重复，保留最早出现的一条，其余记为 `见 E12 00:35`。

### L4 修正检测（最容易翻车的一层）

目标：找出「UP 主后来说的跟前面不一样」的地方。

- 抽取三元组：`(实体, 属性, 值/立场, 时间码)`。例：(`矩阵可对角化条件`, `充分性`, `只需特征值互异`, `E07 12:30`)
- 同一 `(实体, 属性)` 下值冲突 → 候选
- LLM 判定是否「真修正」：可能是①前提变了（"在实数域下"）②口误③概念误用。**只保留高置信度的**
- 输出**中性措辞**："E07 的表述与 E31 不一致"，附双方原文，不做价值判断

⚠️ 这一层的 precision 比 recall 重要得多。错一条就会变成社群攻击的弹药。建议阈值设死：LLM 置信度 < 0.9 一律不输出。

### L5 产出

- `course.md`：大纲 + 每章要点 + `[E12 03:45]` 深链（`https://www.bilibili.com/video/BVxxx?t=225`）
- `index.html`：单页，左侧目录、右侧内容，点时间码跳 B 站。纯静态，无后端
- `contracts/`：`chapters.json`、`points.json`、`claims.json`、`conflicts.json`（供二次开发）
- `stats.md`：总时长、有效时长（去重后）、重复率、修正次数——**这份文件是"尽调"场景的主产物**

## 4. 数据模型（SQLite 单文件）

```sql
episodes(id, bvid, cid, title, duration, pubdate, view, danmaku, series_id)
sources(ep_id, kind, path, model, quality_note)      -- asr | subtitle
chapters(id, ep_id, idx, title, start, end)
points(id, ep_id, chapter_id, text, t_start, t_end, embedding BLOB)
claims(id, ep_id, entity, attr, value, quote, t_start)
topics(id, name, order_idx, parent_id)
topic_points(topic_id, point_id, role)               -- main | prereq | example
conflicts(id, entity, attr, claim_a, claim_b, verdict, confidence)
```

设计取舍：**不用向量数据库**。50 期 × 每期 30 个知识点 = 1500 条向量，全量加载进内存做余弦相似度，毫秒级。引入 Qdrant/Chroma 属于过度工程。

## 5. 成本与性能预算

实测基线（本机，18 核 Ultra 7 251HX / 23.4GB / RTX 5060 8GB）：

| 项 | 实测值 |
|---|---|
| faster-whisper `medium`（CPU） | **1.1–1.2x 实时** |
| faster-whisper `small`（CPU） | 3.5x 实时 |
| 弹幕抓取 | 3 分钟视频 → 1200 条，< 1s |
| 单期转写产出 | 3:17 视频 → 151 句 / ~1.2k 字 |

**50 期 × 30 分钟 = 25 小时音频 → 纯 CPU 跑 medium 需要 23 小时。不可接受。**

三条路，按优先级：

1. **字幕优先**：若 80% 的期有可用字幕，实际要 ASR 的只剩 5 小时 → 5.5 小时。可接受，仍需过夜。
2. **GPU**：ctranslate2 的 CUDA 版跑 `large-v3-turbo` int8，预计 8–15x 实时（**待实测**）→ 25 小时音频约 2–3 小时。这是决定性的优化，值得先花半天验证 cuDNN 9 / CUDA 12 在 Windows 上的坑。
3. **两段式**：先只处理「每期前 3 分钟 + 弹幕峰值段」，20 分钟出"试读版"，用户确认后再全量。体验上很关键——没人愿意等 23 小时才知道跑得对不对。

LLM 成本：50 期 × ~10k input token ≈ 50 万 token，加聚类归并约 20 万，用便宜模型（DeepSeek/GLM 级别）总计**几块钱**。可以忽略。

## 7. 评测方案

先做 **20 期金标**（手工标注章节边界 + 知识点清单），再写代码。指标：

| 指标 | 定义 | 目标 |
|---|---|---|
| 章节边界 F1 | 与人工标注的边界 ±30s 内算命中 | > 0.7 |
| 知识点召回 | 人工清单被覆盖的比例 | > 0.75 |
| 重复检测精确率 | 判为重复的确实重复 | > 0.9 |
| 修正检测精确率 | 判为不一致的确实不一致 | **> 0.95** |
| 深链可用率 | 点击后确实跳到相关内容 | > 0.95 |

前两项可以用 LLM-as-judge 半自动跑；后三项必须人工抽检。

## 8. 风险与合规

| 风险 | 影响 | 对策 |
|---|---|---|
| B 站 wbi 签名/风控（-352） | L0 拿不到列表 | 限速 + 复用现有 UA/Referer 头；预留「手动粘贴 BV 列表」的降级路径 |
| 字幕需登录态 | 拿不到字幕 → 成本翻 10 倍 | 支持用户提供自己的 cookie（本地存，不传输） |
| 版权 | 转写全文属于衍生内容 | 本地生成、默认不分享、不重分发原片；输出只含"要点"和短引用 |
| 修正检测误报 | 变成攻击 UP 主的工具 | 中性措辞 + 高阈值 + 默认折叠 |
| LLM 幻觉 | 知识点张冠李戴 | 每条强制带时间码，UI 上可直接核验 |
| UP 主内容跨主题 | 聚类失败 | 限定「单系列」而非「全站投稿」 |

## 9. MVP 边界与排期

**MVP 定义**：1 个 UP 主的 10–20 期系列，产出 `course.md` + `index.html` + `stats.md`，无 L4（修正检测）。

| 阶段 | 内容 | 估时 |
|---|---|---|
| P0 | GPU 转写可行性验证（turbo 模型 + cuDNN） | 0.5 天 |
| P1 | L0+L1：合集抓取、字幕优先、缓存 | 1 天 |
| P2 | L2：章节切分 + 知识点抽取（prompt 迭代） | 2 天 |
| P3 | L3：聚类 + 大纲 + 去重 | 1.5 天 |
| P4 | L5：静态 HTML + 深链 | 1 天 |
| P5 | 金标评测 + 调参 | 2 天 |
| P6（可选） | L4 修正检测 | 1.5 天 |

合计约 **9 个工作日**（P0–P5），周末项目 ≈ 3 周。

## 10. 待验证的未知数（按优先级）

1. **GPU 转写到底多快**——若 < 5x 实时，方案形态要改（必须强依赖字幕）。
2. **B 站 AI 字幕的覆盖率与质量**——若覆盖率 < 50%，成本模型崩。
3. **章节切分用「弹幕密度 + 口头标记词」够不够**——是否必须上 LLM，影响成本和延迟。
4. **知识点聚类的类数稳定性**——HDBSCAN 参数对结果影响多大，是否需要固定种子 + 人工兜底。
5. **修正检测的可信度**——能否做到 95% precision，做不到就砍掉这个功能。
